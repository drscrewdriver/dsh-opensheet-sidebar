# dsh-opensheet-sidebar

[简体中文](README.md) | [Français](README.fr.md) | [Deutsch](README.de.md) | [Italiano](README.it.md) | [Русский](README.ru.md) | [Español](README.es.md)

> ⛔ **Проект больше не поддерживается (2026-10-01).** В новых версиях хоста DSH есть встроенный предпросмотр office- и табличных файлов в боковой панели, поэтому плагин больше не сопровождается — новых выпусков и адаптации к будущим линиям хоста не будет. Опубликованные версии остаются доступны для установки; для хостов 0.1.x используйте сборки из замороженных веток `compat/0.1.7` / `compat/0.1.5`.

Плагин табличного предпросмотра для правой боковой панели (потребитель [dsh-better-sidebar](https://github.com/omdsh-dev/DSH-better-sidebar)): файлы `csv` / `tsv` / `psv`, как и `xlsx` / `xlsm`, открываются в виде структурированной таблицы, с **защитой типа «предохранитель» (circuit breaker)** — никакой входной файл не может подвесить боковую панель.

> **Имя — каламбур, записан здесь, чтобы его не приняли за опечатку**: `OpenSheet` читается одновременно как «**открыть** таблицу» (open the sheet, глагол) и как «таблица **открытого стандарта**» (open-standard sheet — семейство открытых табличных форматов, идущее от OpenDocument). Одно слово описывает обе его задачи: открыть и прочитать так, чтобы не зависеть от проприетарных библиотек.
>
> Граница: каламбур живёт только в **имени**. Функциональные поля остаются строго буквальными — `exts` получает только реальные расширения (`csv`/`tsv`/`psv`/`xlsx`/`xlsm`), а поля протокола не содержат брендов.

> **v0.2.0 — это переписывание способа интеграции**: клиентская половина v0.1.0 (тогда — `dsh-csv-sidebar`) не соответствовала контракту клиентских модулей DSH (ES-модуль + `activate()` + `ctx.sessionProjections`), поэтому **после установки она не показывалась**. Версия 0.2.0 переделала интеграцию по стандарту plugin-framework — см. ниже «Почему v0.1.0 не показывался».

## 1. Что он делает

| Точка стыковки | Регистрируемое содержимое | Что видит пользователь |
|------|---------|-------------|
| **Просмотрщик файлов** `registerFileViewer` | `exts: ['csv','tsv','psv']`, `priority: 50`, `fetchStrategy: 'fsRead'` | Открываете `.csv` в проводнике → сразу **таблица**, а не сырой текст; включается/выключается в настройках карточки Side, при выключении возвращается встроенный текстовый просмотрщик |
| **Ручная вкладка** `registerTab` | `order: 70`, `single: true` | Страница **CSV** в меню `+`: перетащите или выберите локальный файл; в этот момент **реальный размер в байтах уже известен**, и слишком большие файлы отвергаются до чтения |

Оба используют одно и то же тело отрисовки (полоса предупреждений → полоса статистики → таблица → действия внизу); различие лишь в том, откуда берётся текст.

**Интерактивные возможности** (по принципу «структурированные данные не должны деградировать до чистого текста»): сортировка щелчком по заголовку (по возрастанию → по убыванию → отмена), фильтрация по подстроке, выравнивание числовых столбцов вправо (определяется по образцу), распознавание типа столбца (number / date / boolean / text), закреплённые заголовок и столбец номеров строк, статистика пустых и уникальных значений.

## 2. Четырёхмерный предохранитель

| Измерение | Предел по умолчанию | Поведение при превышении |
|------|---------|-------------|
| Размер файла | 5 MB | **BLOCKED** — для локального файла даже `file.text()` не вызывается; текст, прочитанный хостом, отвергается сразу |
| Число строк данных | 10 000 | **TRUNCATED** — чтение останавливается **на** пределе, без полного разбора |
| Число столбцов | 100 | лишние столбцы отбрасываются + предупреждение |
| Текст ячейки | 10 KB | ячейка сокращается до `前200字符… (+N chars)` + предупреждение |

Кроме того, есть `previewRows: 200`: таблица резервирует DOM-бюджет только на первые 200 строк. С приходом 201-й строки **тишины не будет** — происходит повышение до предупреждения `rows` и установка `TRUNCATED`.

> Результат срабатывания предохранителя — полноценный результат, а не страница ошибки: каждый баннер по отдельности указывает, **какой предел сработал, каково измеренное значение, каков предел**, а таблица продолжает отрисовываться как обычно (при BLOCKED показывается внятное пояснение о блокировке). Все четыре состояния `OK / TRUNCATED / BLOCKED` + `READING` — это отрисовываемые результаты; исключения никогда не выбрасываются, бесконечной загрузки никогда не бывает.

## 3. Сверка со стандартным форматом (plugin-framework)

| Требование стандарта | Этот плагин |
|---------|--------|
| Структура из двух половин | `src/index.ts` (хостовая половина, пустой apply) + `src/client/index.tsx` (браузерная половина) |
| Контракт клиентского модуля | Сборка — это CJS-замыкание `window.__ModuleLoader__.load({ id, factory })`, экспортирующее `apply` + `inject`; **на этапе сборки оно один раз по-настоящему загружается через `node:vm`, и экспорты проверяются assert'ами** |
| Декларативное внедрение `inject` | `export const inject = ['betterSidebar', 'locale']` — apply выполняется только когда оба сервиса cordis готовы; порядок регистрации не важен |
| Жизненный цикл | Все установки идут через `ctx.effect(fn, label)`; при HMR/отключении уборку делает возвращённый disposer |
| Сиды настроек / регистрация команд | Плагин не регистрирует ни сидов настроек, ни команд `/` (следовательно, не затрагивает seat-pin и контракт функции description) |
| Манифест `dsh.bundle` | `package.json#dsh.bundle.patch` + `dsh.client.platform/inject` |
| `cordis.patch.yml` | Чистая строка insert, в комментарии описаны оба способа установки (CLI / вручную) |
| peerDependencies | `@deepseek-ai/*` в диапазоне `>=0.2.0-rc.1 <0.2.1-0` (потолок `-0` — уход от ловушки semver для prerelease); `dsh-better-sidebar` / `react` помечены optional — линия 0.2.0 |
| Структура каталогов | `src/ lib/ assets/ tests/ scripts/` + `screenshots.json` + `dsh.plugin.json` + README/CHANGELOG |
| Ноль зависимостей | **ни одной runtime-зависимости**: парсер CSV и предохранитель — локальные модули; клиентский бандл экстернализует только React (43 KB) |
| Стили | Нет CSS-входа → `styles.css` при сборке инлайнится строкой; `apply` вставляет `<style>` и регистрирует disposer; цвета — исключительно семантические токены `--dsw-alias-*` |
| Многоязычность | Собственное пространство имён `dsh-opensheet-sidebar`, словари zh/en регистрируются через `locale.register(NS, tag, dict)`; без сервиса — откат ко встроенному английскому словарю, без ключа — рендерится сам ключ (видно, а не пусто) |
| Дисциплина мягких зависимостей | Ни одного импорта значений/типов из `dsh-better-sidebar` (`seams.ts` делает только структурные объявления); если `betterSidebar` отсутствует — **громкий warn и пассивное бездействие**, ни полпанели не регистрируется |

## 4. Почему v0.1.0 не показывался (первопричина)

После установки v0.1.0 в профиль `cordis.patch.yml` был прописан, `node_modules` на месте, но боковая панель не подавала признаков жизни, **и в консоли не было ошибок** — модуль отбрасывался уже на этапе загрузки клиентских модулей:

| # | Как было написано в v0.1.0 | Стандартный контракт | Последствие |
|---|--------------|---------|------|
| 1 | `lib/client.js` — **ES-модуль** (`export function activate`) | CJS-замыкание через `window.__ModuleLoader__.load({ id, factory })` | Таблица модулей не получает экспортов → **весь пакет молча не загружается** |
| 2 | Точка входа экспортирует `activate(ctx)` | Экспортировать **`apply(ctx)`** | Даже при загрузке точка входа не находится |
| 3 | Нет `inject` | `export const inject = [...]` | cordis не ждёт `betterSidebar`; момент регистрации случаен |
| 4 | Регистрация через `ctx.sessionProjections.register({key,badge,component})` | `ctx.betterSidebar.registerTab / registerFileViewer` | **не та точка стыковки**: `sessionProjections` — хостовый реестр проекций, а не UI-стык боковой панели |
| 5 | Нет `ctx.effect`; в `package.json` нет `dsh.bundle` / `dsh.client` / `exports` / `files`; peer-потолок записан как `>=0.1.5-rc.1` (без верхней границы) | см. таблицу выше | нет очистки при HMR; метаданные неполны |

> Одной фразой: **дело не в «не сработал», а в «не был загружен»**. Это объясняет и то, почему в системном «просмотре файлов» не видно его записи — этот список и есть реестр `registerFileViewer`.

## 6. Установка

**Способ A (рекомендуется): официальный CLI** — он аккуратно ведёт зависимости и `dsh.profile.bundles` вместе

```bash
dsh plugin --profile <profile> add <path-to-plugin>
```

**Способ B: вручную (три шага, без одного не работает)**

```bash
# 1) Скопировать этот пакет
#    → ~/.dsh/profiles/<profile>/node_modules/dsh-opensheet-sidebar
# 2) Добавить "dsh-opensheet-sidebar" в массив dsh.profile.bundles в package.json профиля
# 3) Дописать строку insert из cordis.patch.yml этого пакета в cordis.patch.yml профиля
```

> ⚠️ **Шаг 2 — самый легко пропускаемый, и его пропуск абсолютно беззвучен.** Слой бандлов синтезируется, только если
> `dsh.profile.bundles` профиля упоминает этот пакет; если сделать только шаги 1 и 3, получится: пакет установлен,
> `- id: dsh-opensheet-sidebar` в `cordis.patch.yml` есть, но этой строке **не на какую строку воздействовать** —
> плагин не загружается, консоль молчит. `disabled: false` из шага 3 лишь «явно включает уже вставленную строку»,
> сам он не вставляет ни одной строки.

**После установки — сначала проверка, потом перезапуск** (никакие службы не запускаются):

```bash
dsh --profile <profile> --dump-config | Select-String dsh-opensheet-sidebar
# Ожидаемый вывод:
#   # == dsh-opensheet-sidebar, patched by ...\cordis.patch.yml
#   - id: dsh-opensheet-sidebar
#     name: dsh-opensheet-sidebar
#     disabled: false
```

Видите эти три строки = строка вставлена + патч профиля действует; теперь достаточно **перезапустить DSH** (бандл профиля и таблица клиентских модулей синтезируются при старте; одного обновления страницы мало).
Не видите = шаг 2 не сработал.

**Зависимость**: `dsh-better-sidebar >= 0.18.1` (опционально). Без неё плагин загружается нормально, пишет warn в консоль и не добавляет ни одной записи.

## 8. Известные границы

- Таблица не делает виртуальную прокрутку: DOM-бюджет жёстко держится `previewRows`; при большем объёме наступает лишь «более ранняя обрезка», замедления не бывает.
- Хостовый `fsRead` сам обрезает большие файлы; в этом случае полоса статистики показывает `≈` и метку «чтение усечено хостом», при `state = TRUNCATED` — **никогда не выдаётся за полный файл**.
- Только предпросмотр, без записи обратно: ни редактирования, ни сохранения.

## 9. Поддержка xlsx (с переключением листов)

`.xlsx` / `.xlsm` открываются тем же табличным рендером; сверху ряд **вкладок листов** позволяет переключаться; скрытые листы (`state="hidden"`) показаны на вкладках приглушённо, по умолчанию автоматически открывается первый видимый лист. Ноль runtime-зависимостей.

### 9.1 Точка стыковки: почему понадобился другой путь чтения

Книга — бинарная, а `fetchStrategy: 'fsRead'` для бинарных данных возвращает только `{kind:'binary', size, truncated, head}` — **без content**, парсеру нечего скармливать. Поэтому xlsx — это просмотрщик, **зарегистрированный отдельно**:

```
fetchStrategy: 'custom'
load: fetch(`/sidebar/file?sessionId=..&cwd=..&path=..`) → arrayBuffer → Uint8Array
```

Идём через собственный маршрут сырых байтов хоста, поэтому ограждение путей рабочего пространства остаётся на стороне хоста (мы сами файлы не читаем). Путь `fsRead` для CSV не тронут.

### 9.2 Конвейер разбора (`src/client/xlsx.ts`)

```
центральный каталог zip → xl/workbook.xml (список листов / порядок / скрытость)
             → xl/_rels/workbook.xml.rels (rId → part)
             → xl/sharedStrings.xml (склейка run'ов форматированного текста)
             → xl/styles.xml (cellXfs → numFmtId → дата или нет)
             → xl/worksheets/sheetN.xml (распаковывается только запрошенный лист)
```

Покрытие ячеек: общие строки / встроенные строки / кэшированные значения формул (`t="str"`) / логические / ошибки / числа; **пропуски столбцов** восстанавливаются по `r="C3"` (отсутствующий столбец не сдвигает следующий); серийные номера дат переводятся в читаемые даты по обеим эпохам — 1900 и 1904.

Распаковка — нативным для браузера `DecompressionStream('deflate-raw')`; XML обрабатывается прицельным сканированием — XML в xlsx представляет собой ровную машинно-генерируемую структуру, универсальный парсер был бы расточительством.

### 9.3 Две барьерные проверки контейнера (для zip одна лишь проверка размера равна отсутствию защиты)

| Барьер | Момент | По умолчанию | Роль |
|------|------|------|------|
| **Заявленный объём распаковки** | **до** любого действия распаковки, чтением центрального каталога | 32 MB на part | заголовок zip можно подделать, поэтому это детерминированный отказ на входе |
| **Потоковый байтовый бюджет** | накапливается в ходе распаковки | всего 64 MB | страховка на случай лжи заголовка; при превышении немедленный `cancel()` |

Если один лист сам по себе превысил лимит, **блокируется только этот лист**, соседние листы открываются как обычно. Контейнер нечитаем сам по себе (не zip / отсутствует part) → `container-error`, рендерится как понятная карточка ошибки, а не исключение.

### 9.4 Пока не поддерживается

`.xls` (Excel 97-2003 BIFF8) и старые форматы WPS `.et` / `.wps` / `.dps`: всё это OLE2-составные документы; при нулевых зависимостях пришлось бы самостоятельно строить разбор CFB (FAT/каталог) + BIFF — дорого и чревато ошибками. Покрытие обычно означает подключение SheetJS (~1 MB, причём версия на npm больше не поддерживается, новые выходят только в официальном CDN), что противоречит принципу нуля зависимостей — при необходимости оценивается отдельно.

> Не путать: **`.xlsx`, который таблицы WPS сохраняют по умолчанию, — это стандартный xlsx**, и данный плагин поддерживает его напрямую; в списке неподдерживаемого только `.et`, полученные через «Сохранить как → старый формат WPS».

## 10. Публикация и миграция идентичности (примеры скриптов)

Два скрипта, каждый ведает своей половиной: **публикация** — на машине разработки, **миграция** — в профиле, где установлен плагин. Оба поддерживают `-DryRun` (единственный режим, который можно запускать повторно), оба останавливаются на первой же неудаче и никогда не «публикуют наперлом».

```powershell
# ① Сторона публикации: сборка + тесты + заслоны идентичности + манифест упаковки, и только затем настоящая публикация (--access public, официальный registry)
pwsh -File scripts/publish-npm.ps1 -DryRun                # сначала посмотреть
pwsh -File scripts/publish-npm.ps1                        # затем публиковать
pwsh -File scripts/publish-npm.ps1 -DeprecateOld dsh-csv-sidebar   # опционально: объявить старое имя deprecated

# ② Сторона потребления: установить новую идентичность → снять старую → сменить id строки патча профиля → проверить по пунктам
#    -NewSpec должна быть spec, «реально разрешимой сегодня» — скрипт предварительно проверяет, прежде чем что-либо менять.
#    Этот пакет пока существует только на GitHub (на npm его ещё нет), поэтому используется форма github::
pwsh -File scripts/migrate-profile.ps1 -Profile web -NewSpec 'github:drscrewdriver/dsh-opensheet-sidebar#<sha>' -DryRun
pwsh -File scripts/migrate-profile.ps1 -Profile web -NewSpec 'github:drscrewdriver/dsh-opensheet-sidebar#<sha>'
#    После публикации на npm перейти на форму registry (до того момента эта строка была бы остановлена предпроверкой):
#    pwsh -File scripts/migrate-profile.ps1 -Profile web -NewSpec 'dsh-opensheet-sidebar@1.0.0'
```

**Предпроверка (preflight)**: `-NewSpec` сначала разрешается, потом начинаются действия — форма npm через `npm view <name>[@range]`, форма `github:` через `git ls-remote` (40-значный SHA по имени не ищется, поэтому проверяется доступность репозитория, а сам SHA проверяет шаг установки), локальная форма — по `package.json`. Если разрешить не удаётся, всё прерывается до резервного копирования с кодом выхода 1 — чтобы пример, «который вроде работает», не падал на полпути.

Можно идти и через алиасы npm script:

```powershell
npm run publish:npm -- -DryRun
npm run profile:migrate -- -Profile web -NewSpec 'dsh-opensheet-sidebar@1.0.0' -DryRun
```

### 10.1 Почему порядок именно «сначала установить новое, потом снять старое»

Переименование затрагивает четыре места сразу, и **пропуск любого одного — это беззвучная неудача** (не ошибка): зависимостная spec профиля, `dsh.profile.bundles` (ведётся reconcile'ом CLI, руками не правится), row id в `cordis.patch.yml` профиля (патч по несуществующему id — пустая операция), каталог в `node_modules`.

Сначала установить новое, потом снять старое — и после неудачи любого шага остаётся **работоспособный плагин**, а не пустой профиль. Оба вызова pnpm автоматически повторяются один раз — при работающем хосте `node_modules` занят, и первая попытка может выбросить `ERR_PNPM_PACKAGE_MANAGER_REMOVE_MODULES_DIR`.

### 10.2 Три ловушки PowerShell 5.1 в скриптах (при повторном использовании экономят полчаса)

| Ловушка | Симптом | Как писать |
|----|------|------|
| Нативная команда + перенаправление `2>` + `$ErrorActionPreference='Stop'` | предупреждения stderr от npm возводятся в **завершающие ошибки**, и скрипт необъяснимо умирает на шаге 2 | перед вызовом временно ослабить до `Continue`, слить потоки через `2>&1 \| Out-String`, затем читать `$LASTEXITCODE` |
| `$PSScriptRoot` в значении по умолчанию `param()` | в момент вычисления это ещё пустая строка → проверка параметров в `Split-Path` падает | значением по умолчанию писать `''`, а разрешать в теле скрипта |
| `.Count` у результата `Where-Object` | один результат — string (без `.Count`), ноль результатов — `$null`; под `Set-StrictMode` сразу `PropertyNotFound` | всегда оборачивать в `@(...)` и только потом брать `.Count` |

Скрипт публикации вдобавок несёт два **заслона, которые должны быть и до, и после загрузки**: имя обязано быть «свободным или своим» (`npm view` + `maintainers` сравниваются с `npm whoami`, чтобы не влезть на чужое имя), а при отсутствии залогиненной сессии — немедленный отказ (вместо ожидания 401).
